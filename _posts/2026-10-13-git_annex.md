[git-annex](https://git-annex.branchable.com/) jest rozproszonym system synchronizacji plików opartym o git.


## inicjalizacja i konfiguracja repozytorium

Po zainicjalizowaniu repozytorium git należy zainicjalizować repozytorium annex.
Można także podać jego nazwę, która pomoże w ustaleniu np. na którym nośniku się ono znajduje.

	git init .
	git annex init

Możliwe jest skonfigurowanie automatyczne dodawanie przez `git add` plików do annex (a nie do git) w oparciu o ich rozszerzenie (podobnie jak ma to miejsce w git-lfs):

	echo '*.mp4 annex.largefiles=anything' >> .gitattributes
	git add .gitattributes

**UWAGA:** dodawanie z użyciem `git add` sposób nie będzie respektować ustawienia `annex.addunlocked == false`.


### tryby

Obecnie domyślnym trybem działania annex jest umieszczanie w repozytorium git w miejsce plików obsługiwanych przez git plików tekstowych wskazujących na obiekt w `.git/annex/objects`.
Git przy operacji checkout podmieni te pliki na kopię plików z `.git/annex/objects`.

**UWAGA:** Na systemach niewspierających „Copy on Write” spowoduje to zwiększenie rozmiaru repozytorium (te same pliki są trzymane w kopii roboczej i w `.git/annex/objects`.
Na systemach obsługujących „Copy on Write” (np. współczesny xfs) problem ten nie wystąpi - do momentu modyfikacji którejś z tych wersji dane na dysku będą współdzielone.
Jednak `du` będzie pokazywał błędny rozmiar - zobacz [du kłamie, czyli copy-on-write i reflink](/2026/10/13/reflink.html).

#### tryb symlink

Annex może działać w trybie symlinków, gdzie w kopii roboczej znajduje się link symboliczny do pliku w `.git/annex/objects`, a plik ten jest ustawiony jako tylko do odczytu.

Możliwe jest wymuszenie tego trybu pracy poprzez:

	git config annex.addunlocked false

W tym trybie `git annex add` przenosi dodawany plik do `.git/annex/objects` a w jego miejsce tworzy link symboliczny.

**UWAGA:** Działa tylko przy dodawaniu pliku poprzez `git annex add` (nie `git add`).


## podstawowe operacje

* (jawne) dodanie do annex: `git annex add PLIK`
* odblokowanie pliku do edycji – zamiana symlinku na kopię (CoW / reflink) pliku: `git-annex unlock PLIK`
* zablokowanie pliku – zamiana na symlink do pliku read-only: `git-annex lock PLIK`
* wyszukanie i listowanie nieaktualnych: `git annex unused`
	* lokalne usuwanie nieaktualnych: `git annex dropunused all`
	* zamiast `all` można określić konretny plik lub zakres podajac numery uzyskane z `git annex unused`
	* używając opcji `--from=NAZWA_REMOTE` operację wyszykiwania i usuwania można wykonać na wskazanym remote
* informacja o tym gdzie znajdują się pliki śledzone przez annex: `git annex whereis`

### annex sync

Do synchronizacji zasobów git annex można używać `git annex sync --content --no-commit`.
Synchronizuje on zarówno gałęzie git jak i pliki śledzone przez annex (jeżeli podano opcję `--content`).
Bez opcji `--no-commit` wykonałby automatycznny commit.

Zachowania domyślne opcji można zmienić przy pomocy `git config`:

	git config annex.autocommit false
	git config annex.synccontent true

Po wykonaniu tych poleceń `git annex sync` zachowa się tak jakby był użyty z opcjami `--content` i `--no-commit`


## zasoby zdalne (remotes)

### standardowy remote git na ssh

	# konfiguracja
	
	git remote add origin ssh://user@host/path/on/remote
	
	# push do remote (zarówno git jak i pliki annex)
	
	git annex push origin

**UWAGA:** Wymagana dostępność `git-annex` także po stronie zdalnej.

Jeżeli nie chemy zby remote git'a był używany przez annex możemy użyć `git config remote.NAZWA_REMOTE.annex-ignore true` po `git remote add NAZWA_REMOTE`.

### remote rsync trzymający katalog roboczy

	# konfiguracja
	
	git annex initremote ZDALNY1 type=rsync rsyncurl=user@host:/path/on/remote encryption=none exporttree=yes
	git config remote.ZDALNY1.annex-tracking-branch GALAZ_SLEDZONA_PRZEZ_TEN_REMOTE
	
	# wysłanie danych do takiego remote
	
	git annex push ZDALNY1
	
	# alternatywnie można wysyłac za pomocą export, np.: git annex export HEAD --to ZDALNY1

### remote rclone trzymający katalog roboczy

Użycie rclone pozwala na korzystanie z wielu różnego rodzaju serwisów do przechowywania plików „w chmurze” (np. MEGA, Google Drive).
Git annex potrafi korzystać z rclone przy pomocy pakietu `git-annex-remote-rclone`, jednak nie pozawala używać opcji `exporttree=yes` (odpowiedzialnej za trzymanie katalogu roboczego, zamiast repozytorium) dla takiego remote.

Rozwiązać to można korzystając z [własnego skryptu](/files/git-annex-remote-rclone-export.sh) implementującego taką współpracę git-annex i rclone.

Skrypt powinien być zapisany jako `git-annex-remote-rclone-export` (bez rozszerzenia) w ścieżce wyszukiwania.
Następnie należy skonfigurować zasób w rclone (przy użyciu `rclone config` lub edycji `~/.config/rclone/rclone.conf`) i dodać remote dla git-annex:

	git annex initremote  NAZWA_REMOTE  type=external externaltype=rclone-export  exporttree=yes encryption=none
	git config remote.NAZWA_REMOTE.rclone-target "NAZWA_ZASOBU_RCLONE:KATALOG_PO_STRONIE_ZDALNEJ"
	
	git config remote.NAZWA_REMOTE.annex-tracking-branch master

Skrypt pozwala też na ignorowanie plików określonych w git config na przykład:

	git config remote.mega.export-ignore ".gitignore .gitattributes"

### remote S3

Git-annex pozwala na korzystanie z remote zgodnych z S3. Remote taki może zostać skonfigurowany tyakże w sposób pozwalajacy na publiczne pobieranie plików:

	git annex initremote NAZWA_REMOTE type=S3 \
		publicurl=https://DOMENA.UDOSTEPNIAJACA.PUBLICZNY.DOSTEP.READ \
		bucket=NAZWA-BUCKETA \
		host=SERWER_S3_DO_DOSTEPU_AUTORYZOWANEGO \
		autoenable=true public=yes encryption=none \
		protocol=https requeststyle=path signature=v4

Można skorzystać z dostawców usługi S3 takich jak cloudflare.com lub backblaze.com (obaj oferują darmowe 10GB, ten drugi w przypadku prywatnego bucket nawet bez podawaniu numeru karty).
W przypadku backblaze.com aby nie mieć ograniczeń transferu ruch należy przepuścić przez cloudflare.com, a workers w tej usłudze pozwalają także na stworzenie proxy umożliwiającego publiczny dostęp do prywatnego bucket - [przykładowy skrypt](/files/BackblazeB2-Cloudflare-worker.js).

## prywatne remote i repozytoria

Standardowo git-annex umieszcza informacje o konfiguracji zasobów zdalnych w plikach `remote.log` i `uuid.log` w gałęzi `git-annex` (można sprawdzić ich treść używając `git show git-annex:remote.log` i `git show git-annex:uuid.log`).

Aby uniknąć tego przy dodawaniu nowego remote należy w `git annex initremote` dodać opcję `--private`.
A w przypadku repozytoriów konfigurowanych przez `git remote` zaraz po ich dodaniu (przed użyciem na nich git annex) należy wywołać `git config remote.NAZWA_REMOTE.annex-private true`.

Aktualne repozytorium może być też ustawione jako prywatne przy pomocy `git config annex.private true` przed wykonaniem `git annex init`.
Tu warto zauważyć ze w przypadku braku tego ustawienia i braku argumentu dla `git annex init` w `uuid.log` zostanie umieszczony opis postaci `user@host:scieżka`.
